## 七、源码侧问题（记录，不修改）

完整清单见 `evidence.md` §四。对读者影响最大的几条：

1. `OrderTimeoutJob#recoverOverdueOrders` 用宿主机时区的 `LocalDateTime.now()`，与 `BusinessTime` 的 Asia/Shanghai 不一致。
2. `ChatInfoService#restoreChat` 对整把 `chat:info:{chatId}` 做 `PERSIST`，会抹掉其他路径设置的 TTL。
3. `RideOrderServiceImpl` 的死代码 `getVehicleMultiplier` 返回 1.30/1.60，与生效的 `RidePricing`（1.60/2.50）矛盾。
4. 没有 MyBatis-Plus 分页拦截器，`/ticket/my/page` 实际不分页且 `total=0`。
5. `TokenServiceImpl#deleteToken` 在 JSON 损坏时跳过索引 `SREM`。
6. `PaymentConfig` 在非自动配置类上使用 `@ConditionalOnMissingBean`，Bean 顺序可能影响默认 503 与自定义实现。
7. `ChatRequestRunner` 的随机 owner 与 `isHeldByThread(owner)` 语义不匹配（静态可疑，未实测）。
8. `getRequiredOrder` 依赖 MySQL 隐式类型转换，非法订单号返回 404 而非 400。

这些都不改变教材结论；教材按"当前实现"描述，并在相应位置提示边界。

### 8.1 同步 HTTP：乘客下单并接单

- **教材路径**：README → 第 1 章 §五（一次真实下单）→ 第 2 章 §二～§五（请求、DTO/Entity/VO）→ 第 3 章 §四（无事务的创建链）→ 第 7 章 §三（创建）与 §五（接单）→ 第 8 章 §二（并发）。
- **前提**：已登录 USER，`POST /order` 带 `Authorization`；高德可用（否则 502）；不要求 Redis/Mongo 可用，但相关副作用会失败。
- **步骤**：`RideOrderController#create` 覆盖 `dto.userId` → `RideOrderServiceImpl#createOrder` 校验/补全 → 高德算路 → 写 Mongo 预览轨迹 → `RideOrderMapper#insert`（`CREATED(10)`）→ 提交后副作用（状态缓存、15 分钟待办、GEO 池失效）→ 返回订单号字符串。
- **源码位置**：`controller/RideOrderController.java#create`、`service/impl/RideOrderServiceImpl.java#createOrder`、`service/base/OrderRouteService.java#addOrder`、`service/base/OrderGrabService.java#syncOrderStatus`、`service/base/OrderDelayQueue.java#schedule`、`service/base/OrderGeoPool.java#add`。
- **结果与可见范围**：HTTP 只返回 `Result.ok(orderId)`，没有 VO；订单真值在 `sys_ride_order`，轨迹在 MongoDB，Redis 只是缓存/待办。创建链**没有** `@Transactional`，Mongo 写入成功而 MySQL 失败时只尝试删除轨迹；清理失败会留下孤儿轨迹（第 1 章 §九已写明）。

### 8.2 Agent：从一句话到订单

- **教材路径**：README → 第 16 章 §二～§五（一次对话与事件）→ 第 17 章 §二～§六（分类、四 Agent、工具循环）→ 第 18 章 §三～§六（报价、暂停、确认、消费、创建）→ 第 23 章 §二（完整旅程复核）。
- **前提**：会话归属校验通过；单轮执行锁可用；分类模型与对话模型可用；用户已确认报价。模型的具体措辞是教学题设，不保证真实模型这样输出。
- **步骤**：`ChatController` → `ChatRequestRunner#run` 抢 `chat:execution:{chatId}` → `ChatServiceImpl#chat` 限流/归属/`break` 检查/分类 → `OrderAgent` 工具循环 → `OrderTool#getEstRouteAndPrice` 报价并写 `quoted` → `notifyUser` 暂停并保存 → 用户 `POST /r/{id}` → `ChatServiceImpl#resume` → `OrderConfirmation#confirm` 写 `ReadyForCreate` → `OrderAgent#resume` → `OrderTool#createOrder` 组装 DTO → `consume` → `RideOrderService#createOrder` → `lockChat`/写 `OrderId`。
- **源码位置**：`service/base/ChatRequestRunner.java#run`、`service/impl/ChatServiceImpl.java#chat/#resume`、`agents/OrderAgent.java#resume`、`service/base/OrderConfirmation.java`、`agentbase/tool/OrderTool.java#createOrder`。
- **结果与可见范围**：客户端看到 `tool_start`、`confirm`、`message` 等 SSE 事件；`confirm` 的载荷是 JSON 字符串。真正的授权在服务端 Lua（`confirmedQuote == quoteId == ReadyForCreate` 且年龄 ≤ 900000 ms），提示词里的"必须确认"不是授权。模型输出、事件是否送达、HTTP 是否已提交都不由业务代码保证。

### 8.3 并发/缓存：两名司机抢同一单，同时附近池失效

- **教材路径**：README → 第 8 章 §二～§五（两把锁、Lua、条件更新、失败矩阵）→ 第 9 章 §三（GEO 池失效与重建）→ 第 14 章 §五（缓存竞争时间线）→ 第 23 章 §2.5（接单追踪）。
- **前提**：订单 10 且 `driver_id IS NULL`；两名司机都通过 DRIVER 切面且账号有效；Redis 可用；两人几乎同时提交。
- **步骤**：T1/T2 各自进入 `@Transactional(READ_COMMITTED)` + `order:lock:{id}`（等待上限 3 秒）→ `tryGrab` 先锁 `sys_user` 司机行、再查该司机活跃单并修复 `driver:active`、再读/回填 `order:status` → `GRAB_ORDER_ATOMIC`：先到者把 `driver:active` 写成订单号，后到者读到非 `__IDLE__` 返回 -2 或状态不符返回 -1 → 先到者执行 DB 条件更新（`status=10 AND driver_id IS NULL`），影响 1 行才算成功 → 提交后 `syncOrderStatus(20)`、`orderGeoPool.remove`、`schedule(10 分钟)`。
- **源码位置**：`service/impl/RideOrderServiceImpl.java#driverAcceptOrder/#withOrderLock`、`service/base/OrderGrabService.java#tryGrab/#rollbackGrab/#releaseDriver`、`util/RedisScripts.java#GRAB_ORDER_ATOMIC/#SYNC_ORDER_STATUS`、`service/base/OrderGeoPool.java`。
- **结果与可见范围**：后到者拿 409（司机忙或订单不可抢）；先到者只有在 DB 影响 1 行后才返回 `true`。若预检成功但 DB 0 行（缓存陈旧/并发取消），会 `rollbackGrab + refreshOrderStatus` 并返回 `false`（HTTP 200）。Redis 预检不是裁决，DB 条件更新才是；`order:status` 缓存与 GEO 池都是可失效的加速结构，失效后回表。
