### 1.3 本阶段最重要的五个裁决

1. **诊断报告的 Git 时间线 hash 是准确的**。子代理曾质疑 `8d5d574` / `bdc40d7` / `153c511` 不存在；经 `git log --oneline --all` 亲自复核，三者均真实存在。但报告**漏了关键事实**：仓库有两条被重写过的分支（旧分支 `8d5d574 → … → bdc40d7 → 3f952ee → 61ce2be`，新分支 `3a13c56 → d534157 → … → 153c511 → ef4abf1 → 75a68df(merge) → a8f4e33`），存在同 message 不同 hash 的重复提交，这正是「文档基准 commit 与当前源码行号大面积错位」的根因。
2. **`README.md` L59「工具结果指针化」不能被判为过时**。`ToolRepPointerTool.java:22-30` 的 `getCalling`、`recordCalling:33-54`、`ChatProperties.java:92-93` 的提示词契约都完整存在；正确表述是「历史消息改为保存全文，`ToolResponseMemory` 退化为按 `(callId, chatId)` 反查的**辅助索引**」，不是「指针化已取消」。诊断报告自身 L123 的建议文案其实写对了，L500 的断言与之矛盾。
3. **墓碑机制是「部分实现」，不是「已落地」**。`CityCodeUtil.invalidate(String)`（`CityCodeUtil.java:106-114`）在生产代码**零调用方**，只有 `RedisCacheRegressionTest.java:208,215` 调用。全库 `invalidate(` 的其余命中是 `OrderGeoPool` 的同名私有方法。按「不允许把历史设计方案描述成当前已实现能力」的要求，文档必须标注「机制已就位并通过测试，城市表写路径未接线」。
4. **`docs/01` 不是纯规划稿**，而是「规划稿 + P1-3 事后补记」的混合体：抬头声称基于 `8d5d574`，但 L218-233 描述的 `TicketPoolIndex` 由后续 `8fdcbc5`/`26f353d` 才引入；且 L283 优先级表仍把「工单池 ZSet」列为待实施，与 L220「已实现」自相矛盾。因此不能对整篇统一加「改造前快照」标注，否则会误伤全篇唯一准确的段落。
5. **`a8f4e33` 实际新增 16 个 Java 主源码类**（`git show --name-status` 的 A 记录），不是报告写的「8 个核心类」；报告 L33 自己列了 9 个，仍未含 `PaymentVerifier`、`BusinessTime`、`CredentialStamp`、`QaSyncJob`、`QaSyncJobMapper`、`AgentStreams`、`MessageWindow` 等。这批新增类恰好是学习文档的最大知识空白。
